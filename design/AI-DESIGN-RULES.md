# Civilis 后续 AI 设计与交付规范

> 本文是后续 AI 继续开发本项目时的执行规范，覆盖设计方法、架构边界、验证标准和 GitHub 交付流程。若本文与代码冲突，先确认真实代码行为，再同步修正文档。

## 1. 接手任务

1. 先读根目录 README、design/03-architecture.md、design/game/README.md、design/game/DEV-GUIDE.md。
2. 阅读当前目标时代的设计文档和开发清单。
3. 执行 git status --short、git log -5 --oneline，确认已有改动和最近阶段。
4. 使用 rg 搜索相关类型、状态字段、纯函数、UI 入口和测试，不要凭文件名猜架构。
5. 先复现用户报告的问题，再修改代码。
6. 不得重置、覆盖或删除用户已有的未提交改动。

## 2. 总体设计方法

本项目是纯前端、长时间运行的文明演进放置游戏。设计优先级如下：

- **可达性优先**：任何科技、资源、岗位或时代条件都必须有可执行的启动路径，禁止 A 依赖 B、B 又依赖 A 的死锁。
- **时代引入新动词**：时代不能只是数值变大，必须引入新的动作、新瓶颈或新决策。
- **继承优先于重置**：跃迁默认只新增内容，不清空资源、人口、建筑、岗位和文明积累；只有新机制计时器可按设计初始化。
- **数据驱动**：时代、科技、岗位、建筑、资源和常量放在 data，不在 UI 复制规则。
- **纯函数优先**：计算、验证、结算和跃迁规则放在 game，状态写回集中在 state/store.ts。
- **玩家可解释**：失败必须说明原因，资源为 0、科技不可研究、贸易中断、岗位未解锁和条件不足都要可见。
- **小步验证**：每组改动都能独立回归、构建和提交，避免跨多个系统的大型不可验证改动。

## 3. 架构边界

| 层 | 目录 | 责任 | 禁止事项 |
|---|---|---|---|
| 数据 | demo/src/data | 资源、科技、岗位、建筑、时代、常量 | 不在 UI 复制数据 |
| 规则 | demo/src/game | 纯计算、研究、生产、贸易、记录、跃迁、模拟 | 不直接调用 React 或 Zustand |
| 状态 | demo/src/state/store.ts | Zustand 状态、用户操作、规则落库、消息 | 不把复杂规则散落到组件回调 |
| 基础设施 | demo/src/core | 时钟、存档、随机数、格式化 | 不绕过统一时钟和存档入口 |
| UI | demo/src/ui | 展示、交互、响应式布局、反馈 | 不重复实现引擎条件 |
| 验证 | demo/src/dev | 回归、模拟、可达性测试 | 不用手工结果替代断言 |

标准数据流：

    data -> game pure functions -> state/store -> UI
                             \\-> dev regression

新增系统优先新建独立规则文件。记录使用 game/record.ts，贸易使用 game/trade.ts，不要无边界膨胀 engine.ts。

## 4. 时代、科技和资源

### 4.1 时代

- EraId、ERAS 和时代序号必须一致。
- 时代条件统一由 checkAdvance() 检查，UI 直接呈现结果，不重复写条件。
- advanceEra() 只能在条件全部满足且存在下一时代时成功。
- 尚未实现的时代显示“交接待开放”，不能伪造完整可进入状态。
- 跃迁应产生结构化 GameEvent，再由状态层翻译成消息。
- 当前 E3 是最后一个已实装时代；E3→E4 只做条件可达性验证，除非明确开始 E4，不实现空壳 E4。

### 4.2 科技

- 科技必须有唯一 id、时代、成本、类型、前置、效果和说明。
- 研究资格只能由 game/engine.ts 的 canResearch() 判断。
- E3 的“知识”不是第二个状态字段，而是 state.experience 的显示名称，禁止新增 knowledge 并行字段。
- 研究货币名称使用 researchCurrencyName()，组件不得硬编码时代判断。
- 新科技必须验证前置可达、成本可获得、研究后内容可使用。
- 首项科技必须有启动产出或过渡机制。E3 楔形文字研究前保留低速文明积累，研究后切换到书吏产出。

### 4.3 资源

- 加入资源时同时检查 ResourceId、RESOURCES、排序、生产、存储、消费和存档迁移。
- 资源栏采用渐进显隐：初始只显示早期资源，后续资源必须由时代和相关科技解锁。
- 不得仅因资源加入数组就提前显示一排 0。
- 资源容量、生产速率和 UI 显示必须来自同一套引擎规则。
- 本地生产、贸易进口、岗位条件、贸易邻邦和资源说明必须一致。

## 5. 模拟、时钟和存档

- 在线、离线和测试模拟共享 game/simulation/ 与 engine.tick()。
- 随机数使用可保存、可复现的 RNG。
- tick 顺序保持：资源生产、贸易/救急、人口与消耗、季节/事件、状态写回。
- 新字段必须有旧存档默认值和迁移逻辑，并更新 SAVE_VERSION。
- 跃迁不得偷偷清空玩家积累；只初始化新机制所需的计时或字段。
- 离线结算必须验证与在线等效时长一致，并有时长上限和效率系数。

## 6. UI 规范

- 支持竖屏抽屉模式和横屏三栏模式。
- 横屏结构：左侧资源/状态，中间主要操作，右侧消息反馈。
- 左右栏可收缩，中间区设置最小可读宽度，避免科技树被挤压。
- 资源条单行横向滚动，不换行撑高页面。
- 页面使用无框列表和细分隔线；卡片只用于重复项、弹窗和确实需要边界的工具。
- body 固定视口，内容区自行滚动，避免多重页面滚动条。
- 主界面优先展示当前能做什么、缺什么、下一步是什么；历史信息默认折叠。
- 数字使用等宽字体和固定列宽，避免 tick 更新造成布局抖动。
- 研究、建造、派人、开路线等有成本动作必须有确认或失败反馈。
- E3 科技显示成本、知识存量、可研究状态和失败原因。
- E3 知识为 0 时必须说明是楔形文字未完成还是没有书吏。
- 贸易显示价格、趋势、运输类型、路线状态、契约和中断/拒交原因。
- 时代条件逐条显示完成状态和进度。

## 7. 测试验收

每个功能按风险覆盖：

1. 纯函数：公式、前置、资源显隐、迁移和条件检查。
2. tick 回归：产出、消耗、贸易、人口和事件写回。
3. 可达性：从启动状态到目标科技/时代存在路径，不能只构造目标状态。
4. 构建：TypeScript 无错误，Vite 构建成功。
5. 差异：git diff --check 通过。

标准命令：

    cd D:\\try\\game\\demo
    npm run regression
    .\\node_modules\\.bin\\tsc.cmd --noEmit
    .\\node_modules\\.bin\\vite.cmd build
    cd D:\\try\\game
    git diff --check
    git status --short

E1/E2 基线不得因 E3 或后续时代改变。新增时代规则必须门控，并覆盖旧时代回归。

## 8. Git 与 GitHub

- 一个稳定功能组一个提交，提交前完成回归、类型检查、构建和 diff 检查。
- 使用简洁英文 Conventional Commits，例如 feat:、fix:、test:、ui:、docs:。
- 不把无关格式化、生成文件和临时文件混入提交。
- 提交前检查 git status --short 与 git diff --stat，确认只包含本阶段文件。
- 当前远程为 origin，分支为 main，远程为项目既有 GitHub 地址。

标准流程：

    cd D:\\try\\game
    git status --short
    git diff --check
    git add <本阶段相关文件>
    git commit -m "<type>: <short description>"
    git push origin main
    git status --short

推送后必须报告提交 SHA、验证结果和未完成边界。只推送用户明确要求的项目远程；不得写入 Token、密码、Cookie 或其他凭据。GitHub 上传成功不代表功能完成，仍需本地验证。

## 9. 禁止事项

- 禁止用第二个 knowledge 字段解决 E3 知识问题。
- 禁止无条件显示 E3 资源，导致早期出现 0 值资源。
- 禁止只改科技成本文案，不验证产出和扣除字段。
- 禁止首项科技依赖自身解锁的岗位或资源。
- 禁止在组件中复制 checkAdvance、canResearch 或贸易结算规则。
- 禁止为实现新时代改写 E1/E2 已通过的公式和常量。
- 禁止用随机起始结果代替可达性证明；随机机制必须可复现。
- 禁止 E4 未实现时显示可点击但没有完整规则的 E4 按钮。
- 禁止使用 git reset --hard 或 git checkout -- 覆盖用户改动。
- 禁止在未完成修改、测试、提交、推送和状态确认前结束阶段工作。

## 10. 阶段交付报告

每阶段报告应包含：

- 完成的功能、文件范围和玩家可见变化。
- 新增或修复的回归场景。
- npm run regression、tsc、vite build、git diff --check 的结果。
- GitHub commit SHA、提交信息和 push 结果。
- 尚未实现或明确阻塞的边界。

本规范应与代码一起维护。架构、时代规则、交付流程或用户已拍板设计发生变化时，先更新本文再扩展功能。
