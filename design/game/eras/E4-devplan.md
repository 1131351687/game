### T2 · 引擎层（`src/game/engine.ts`，纯函数优先）

> ⚠️ **铁律：所有 E4 新机制必须时代门控**（如 `state.era >= 'E4'` 或在 `aggregateEffects` 内按时代累加），
> 否则会污染 E1/E2 的既有基线（1163s / 1920s）与 SSR 字节一致性。E1/E2 的代码路径字面上不得改动。

- [ ] **T2.1 铁 / 铸币 产出接入**（本代产出基础）
  - `calcJobOutput` 增加 铁矿工 / 铸币工 分支（沿用 `scaledByTool` 与 `jobMultiplier` 框架）
  - 铁矿工的"铁器世代"门禁**不能**复用 E1 `toolTier`（语义冲突见 §四·4）；改为新效果键 `ironTier`，由 E4「钢铁」「铁制农具」赋予
  - **验收**：E1/E2 的 `calcJobOutput` 行为逐字节不变；E4 中铁/铸币能按岗位数产出

- [ ] **T2.2 研究货币承接（E3 知识）**
  - `getResearchCurrency(state)`：E1/E2 → `experience`；E3+ → `knowledge`
  - `calcKnowledgeOutput(state)`：E4 采用设计 §11.3 **人口 × 0.012 × 政体制数（研究系数）**（书吏模型在 E4 是否保留见 §四·3）
  - **E4 起「经验」不再产出**（设计口径延续 E3），但 `experience` 字段保留以免旧存档报错
  - **验收**：E1/E2 的 `calcExperienceOutput` 行为逐字节不变；E4 知识产出随人口×政体制数变化

- [ ] **T2.3 版图与规模不经济**（核心机制一）
  - `getAdminLoad(state)`：A(n)=1.5·n^1.5；R(n)=1+(0.030−0.006·D)·(n−1)；Λ(L)=max(0.70,1−0.02L)；A_eff=A·R·Λ
  - `getStabilityRate(state)`：ρ = 0.80·A_eff/(A_eff+240)·(1+0.6·δ)，δ=max(0,1−κ)
  - 仅 E4 及以后生效（**铁律：时代门控**）
  - **验收**：n=20, D=0, L 取需求值时 ρ≈37.4%（对照设计 §1.3 表）；n=24, D=4 时 ρ≈36.4%

- [ ] **T2.4 治理覆盖率 κ 与秩序 O**（核心机制二 / 仪表盘）
  - `getGovernanceSupply(state)`：G = B×E（B=官吏数，E=治理效率）
  - `getCoverage(state)`：κ = G / A_eff
  - `getOrderDelta(state)`：dO/dt = clamp(15·(κ−0.8), −8.0, +3.0) × 政体秩序恢复系数；κ≥1 额外 ρ 减免
  - 秩序档位（太平 80+ / 安定 50+ / 骚动 20+ / 叛乱 1+ / 崩解 0）的产出/研究/扩张许可乘子由 `getOrderRegime(state)` 返回
  - **验收**：构造 κ=1.0 → dO/dt=+3.0；κ=0.5 → −4.5（clamp 下限）；κ=0.8 → 0

- [ ] **T2.5 政体系统**（E4 首次登场）
  - `getPolity(state)` / `canSwitchPolity(state)` / `applySwitchPolity(state)`：一次性铸币 200,000、秩序 −25、冷却 900s
  - 政体解锁于支撑科技「郡县制」（`reveal` 门控：E1–E3 不出现政体 UI）
  - 三政体各系数（σ/兵员/铸币/研究/秩序恢复/秩序上限/独特规则）从 T1.6 数据读取
  - **验收**：未研究郡县制时政体函数返回"未解锁"；切换后冷却期内拒绝二次切换

- [ ] **T2.6 铸币三层依赖链**（防无脑扩张）
  - `tickCoinSpend(state, dt)`：官吏俸禄 0.15/秒/岗 + 军团军饷 0.8 铸币/秒/军团（持续扣除，余额不足时触发欠饷状态→秩序压力）
  - 依赖链：铁（铁矿工）→ 铸币厂（建筑）→ 铸币工（岗位）→ 官吏/军团（支出）
  - **验收**：无铸币厂时铸币工无法上岗；官吏/军团在铸币耗尽后不再被"免费养着"

- [ ] **T2.7 扩张动作与平定期**
  - `canExpand(state)`：秩序 O≥50、军团数 L≥⌈0.15·n^1.15⌉、共和额外 官署≥⌈n/3⌉
  - `expandTerritory(state)`：一次性铸币 800·n^1.3 + 铁 200·n^1.1；平定期 (15+2n) 秒，期间 A_eff×1.5
  - 放弃领土（可撤销）：n−1，回退相应 K 与 A_eff
  - **验收**：n=1→2 需 L≥2（⌈0.15·1^1.15⌉=1→实际表给 n=3 时 L_req=2，边界按设计表校准 TODO(balance)）；秩序<50 时 `canExpand` 返回具体 reason

- [ ] **T2.8 人口模型 E4（r / K）**
  - K = K_base(200) + Σ住所容量 + 60·n^0.85（版图提供递减承载力）

### 3.2 引擎新增函数（签名与公式）

| 函数 | 公式 / 行为 | 边界情况 |
|---|---|---|
| `getAdminLoad(state)` | A=1.5·n^1.5；R=1+(0.030−0.006D)(n−1)；Λ=max(0.70,1−0.02L)；A_eff=A·R·Λ | 仅 `era>='E4'` 计算，否则返回 0（门控） |

### 3.3 `tick` 的执行顺序（E4 分支，顺序错会算错账）

```
// 仅当 state.era >= 'E4' 时执行以下 E4 补充块（在现有 E1/E2 tick 之后追加，
// 不改动既有返回字段的语义）；E1/E2 完全走原路径。
1  资源产出（food/wood/stone/iron/coin/livestock/fabric 含岗位×衰减×季节）
2  资源消耗（人口吃粮 0.25/s·人；官吏吃粮 1.2/s·岗；军团吃粮 2.0/s·军团）
3  铸币持续支出（官吏俸禄 0.15/s·岗 + 军团军饷 0.8/s·军团）—— 先于人口结算，
       因为"养不起官=秩序崩"是 E4 的核心约束，必须当 tick 立即体现
4  人口增长（r × P × (1−P/K) × 食物因子；K 含 60·n^0.85，r 含 安定因子）
5  治理与秩序（算 A_eff→G→κ→ρ→dO/dt→order；应用 order 档位乘子到产出/研究/扩张）
6  扩张/平定期计时（expansionPending 到期则 territory+1、A_eff 复原）
7  政体切换冷却计时（polityCooldownUntil 递减）
8  统计
```

> ⚠️ **为什么铸币支出排在人口之前**：E4 的"无脑扩张"陷阱正是靠持续支出堵住的——若俸禄/军饷晚一拍扣，玩家会在铸币已亏空时仍看到满员官吏，扩张决策失真。这与 E3「贸易先于人口」同理（见 E3-devplan §7.3）。

## 四、待拍板事项 · 推荐方案

> 每项给推荐与理由。**你只需回"按推荐"或指出要改哪条**，不用逐条写方案。

### 4.1 ⚠️ 起始状态口径错配（E4 §11.1 vs 跃迁只新增不重置）—— **推荐：起始状态表整体重对齐，人口/资源继承 E3 末态**
- **矛盾**：E4 §11.1 写"起始人口 1,000、粮食 5,000、木材 3,000、知识 2,000"，但 E3 末态人口约 **2,160**，且铁律「跃迁只新增不重置」要求资源/人口原样带过。设计文档的起始表是"假设从零推演"的占位值，与交接铁律直接冲突。
- **推荐**：E4 起始表改写为"交接继承 + 新初始化"两段式——人口=继承 E3 末态（约 2,160，最终值待 E3 实装后校准）、食物/木/石/知识=继承 E3 末态、铁=0、铸币=0、秩序=70、版图=1、政体=null。铁/铸币/秩序/版图/政体是 E4 **新状态**，初始化不算"重置旧内容"。
- **理由**：遵守用户明示的口径错配处理要求（"不要悄悄照抄"）；否则玩家会在跃迁瞬间人口从 2,160 被砍到 1,000，违反层层递进体感。
- **备选**：若坚持设计文档的 1,000 起点，则必须放弃"只新增不重置"对人口的特殊处理，并显式说明理由——不建议。

### 4.2 政体制数两组不一致（§11.3 vs §3.1）—— **推荐：统一为 §3.1 的研究系数，人口增长率另立一组并显式命名**
- **矛盾**：§11.3 把"政体制数"写为 君主 0.90 / 共和 1.10 / 神权 0.85 并用于人口增长率 r；但 §3.1 政体表给的是**研究系数**（君主 −10% = 0.90 / 共和 +15% = **1.15** / 神权 −20% = **0.80**）。两组数值本身不一致（共和 1.10 vs 1.15、神权 0.85 vs 0.80），且分别作用于 r 与知识产出，文档未说明。
- **推荐**：
  - 研究/知识产出系数采用 §3.1：君主 0.90 / 共和 1.15 / 神权 0.80（已是 §11.7 验算的口径）。
  - 人口增长率 r 的"政体制数"**另立一组**，定义为 `polityGrowthMul`：君主 0.90（快而不稳→增长基准）/ 共和 1.10（稳而研究型）/ 神权 0.85（守成型）；在 §11.3 显式标注这是"增长率专用"而非研究系数，消除歧义。
- **理由**：§11.7 配平验算（共和全时代 6,700,000、君主 5,250,000）已用 §3.1 研究系数，改动会牵动全局配平；人口增长率另立一组不影响研究配平。
- **备选**：全部用 §11.3 的 0.90/1.10/0.85 同时作用于研究与增长——但需重算 §11.7 全部数字，工作量大且动摇已定稿的"取舍成立"结论。

### 4.3 书吏（E3 核心岗位）在 E4 的去留 —— **推荐：E4 书吏退役，学识改为"人口×0.012"扁平产出（与铁律"岗位可退役进阶"一致）**
- **矛盾**：E3 的核心新岗位是**书吏**（知识产出 0.15/秒·人）；但 E4 §7 岗位集只列 5 个岗位（不含书吏），§11.3 又把学识产出改为"人口 × 0.012/秒"。书吏若凭空消失，既违反"岗位可退役进阶"铁律的可见性，也让 E3 的刻录/书吏投资在 E4 失去意义。
- **推荐**：E4 起书吏**数据退役**（`isJobRetired` 声明，人数回闲置池，不掉人口），并在跃迁消息中明确"文字已成基础设施，学识改为按人口自然产出"。E4 的学识产出采用 §11.3 扁平公式（人口×0.012×政体制数）。
- **理由**：符合铁律"岗位可退役进阶"（E2 采集者→农夫、E3 书吏→基础设施 是同一模式的延续）；E4 人口达十万级，书吏逐一产出不再合理，扁平模型更可解释（铁律"数字可解释"）。
- **备选**：保留书吏并叠加扁平产出（双来源）——但会导致 E3 书吏投资在 E4 仍有效、与"知识产出重构"的设计意图冲突，且配平面复杂。

### 4.4 「铁器世代 ≥1」与 E1 toolTier 语义冲突 —— **推荐：新增独立 `ironTier` 效果键，由 E4「钢铁」「铁制农具」赋予**
- **矛盾**：E4 铁矿工要求"铁器世代 ≥1"，但引擎现有 `toolTier` 由 E1 科技赋予（tier1=削尖木矛，是木/石工具世代）。若直接复用 `requires.toolTier>=1`，E4 铁矿工会因 E1 木矛科技而**在 E1 时代就满足门禁**，语义完全错位。
- **推荐**：在 `aggregateEffects` 新增 `ironTier` 键（默认 0），由 E4「钢铁」（设 ironTier=1）与「铁制农具」（提升）写入；`isJobUnlocked` / `calcJobOutput` 对铁矿工改用 `ironTier`。E1 的 `toolTier` 保持不动。
- **理由**：避免跨代门禁泄漏；铁器世代是 E4 自己的物质前提，不应被远古木矛满足。
- **备选**：复用 `toolTier` 但规定"E4 起 toolTier 清零重算"——但会破坏 E1/E2 工具世代加成在 E4 的衰减继承，牵动既有配平。

### 4.5 P1 文明重启完整规格缺失 —— **推荐：引用 P1 专属设计文档落实，本计划仅预留接口**
- **矛盾**：E4-empire.md **未包含** P1 文明重启的详细设计（遗产点递减公式的精确曲线、保留/失去清单的具体条目、UI 布局），仅用户简报给出摘要（遗产点 +3% 全局产出递减、保留/失去清单、UI）。
- **推荐**：本计划在 T2.10 / T4.10 预留 `p1Unlocked` 与 `getLegacyBonus` 接口，**待引用 P1 设计文档后**再填充具体遗产点曲线与保留/失去清单；当前先以"首次跃迁到 E4 解锁 + 全局产出 +3%×legacyPoints（递减待定）"占位，标 `TODO(p1-spec)`。
- **理由**：不在 E4 文档里凭空编造 P1 规则；P1 是跨代系统，应有独立设计文档。
- **备选**：直接在 E4 计划里拍定 P1 全部数值——但用户明确要求"计划必须包含 P1 实装任务"而非"设计 P1"，故只实装不设计。

### 4.6 代码基线 SAVE_VERSION 已为 6 但 era.ts 仅 E1/E2 —— **推荐：开工前确认 E3 是否已接入 `ERAS`**
- **矛盾**：`store.ts` 的 `SAVE_VERSION=6`（即 E3 计划落地值），但 `data/era.ts` 的 `EraId` 仅 `'E1'|'E2'`、`ERAS` 无 E3/E4。两者不一致，可能 E3 仅做了版本号占位而未接入时代类型系统。
- **推荐**：本计划以"E3 已接入 `ERAS`（SAVE_VERSION=6）"为前提，E4 在其上把 `EraId` 扩为 `'E1'|'E2'|'E3'|'E4'`、SAVE_VERSION 升 7。开工前先确认 E3 实际状态；若 E3 未接入，本计划需前置于"先接 E3"。
- **理由**：E4 的大门是 E3（门槛「印刷术」由 E3 的"钢铁"推开），E3 不接入则 E4 无从触发。
- **备选**：把 E3 接入与 E4 合并到一个大 PR——但体量过大、回归面爆炸，不建议。
