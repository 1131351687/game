### T2 · 引擎层（`src/game/engine.ts`，纯函数优先）

> ⚠️ **铁律：所有新机制必须时代门控**（`state.era !== 'E1'` / `>= 'E3'` 之类），
> 否则会污染 E1/E2 的既有基线（1163s / 1920s）与 SSR 字节一致性。

- [x] **T2.1 记录容量与刻录**（本代核心机制）
  - `getRecordCapacity(state)` = `3 + 学宫×5 + 泥板制作加成 + 档案库扩建加成`
  - `getUsedSlots(state)` = 已刻录科技数
  - `canRecord(techId, state)` → `{ok, reason}`：① 有空槽 ② 知识 ≥ cost×10% ③ 至少 1 名书吏
  - `recordTech(techId, state)`：扣知识、占槽、把科技从"口头"升为"已刻录"（**不可撤销**）
  - 科技效果口径：**口头 ×50% / 已刻录 ×100%**，并叠加既有的 `eraDecay`
  - **验收**：槽位满时 `canRecord` 返回明确 reason；未刻录科技在 E4 起失效（T3.4 验证）

- [x] **T2.2 研究货币切换**
  - `getResearchCurrency(state)`：E1/E2 → `experience`；E3+ → `knowledge`
  - `calcKnowledgeOutput(state)`：书吏产出 ×（1 + 书吏训练/六十进制加成）
  - **E3 起关闭「经验」产出通道**（设计明确），但 `experience` 字段保留以免旧存档报错
  - **验收**：E1/E2 的 `calcExperienceOutput` 行为逐字节不变

- [x] **T2.3 铜 — 锡 — 青铜生产链**
  - `calcResourceOutput` 支持铜/锡/青铜；锡矿带的本地锡产出按铜矿工效率的一半计
  - 冶炼工的投入约束：铜/锡不足时**按比例降速**（不是报错，而是"缺料停工"）
  - 再生冶炼（回收率 30%）与熔炉（+25%）进入 `aggregateEffects`
  - **验收**：无锡时冶炼工产出为 0 且 UI 能说明"缺锡"

- [x] **T2.4 贸易路线**（全新区块，建议先在控制台跑通再上 UI）
  - 数据：4–6 个虚拟邻邦（产出 / 需求 / 距离 1–3）＋ 路线槽位（商栈 +2）
  - `tickTrade(state, dt)`：运力（商人）÷ 距离系数 → 换得货物；价格随买卖浮动（买多则贵）
  - 声望（0–100）修正全部价格；契约可锁价 5 分钟（「契约刻录」延长到 12 分钟）
  - 每条活跃路线需 **40 名书吏**（「账目分类」降到 30）—— 这是"书吏占用"的第二条出口
  - **验收**：能跑出"铜富余但没有锡 → 必须开路线买锡"的完整链路

- [x] **T2.5 规模递减（N^0.9）**
  - `effectiveOutput = unitOutput × N^0.9`，**仅 E3 及以后生效**
  - **验收**：E1/E2 输出公式字面上未变（可用 SSR 字节比对 + `autoplay beeline` 1163s 佐证）

- [x] **T2.6 跃迁条件扩展**
  - `checkAdvance` 需支持：`研究「钢铁」+ 已刻录`、人口 ≥1800、青铜 ≥2000、学宫 ≥3、商栈 ≥2、**已刻录 ≥12 项**
  - 复用已有能力：`minBuildings`（多建筑门槛）已就绪，需再加"已刻录计数"类条件
  - **验收**：六项条件在 UI 上逐条显示 ✅/⬜ 与进度

**T2 验收**：为以上六个子系统各写一段可跑的验证脚本（放进 `src/dev/`，跑完即删），
证明"新机制正确"且"旧机制未变"。

- [x] **T3.3 离线结算含贸易**

- [ ] **T3.4 跨代失效验证**

  - **验收**：构造一个"只刻了 3 项"的 E3 终态 → 在 E4 检查未刻录科技确实不生效

## 七、实施级规格（T1–T4 的落地细节）

> 本节把上面的任务分解落到**字段 / 函数签名 / tick 顺序**级别。数值全部来自 `E3-citystate.md` §11。

### 7.1 状态层新增字段（`GameState`，SAVE_VERSION 5 → 6）

```ts
// 资源（全部进 TopBar 资源栏，按时代显隐）
knowledge: number;   // 知识：E3 起的研究货币（书吏产出 0.15/秒/人）
copper: number;      // 铜：铜矿工产出；本地无矿则恒为 0（只能贸易）
tin: number;         // 锡：普通地形依赖贸易，锡矿带可少量自给
bronze: number;      // 青铜：冶炼工产出（铜 0.9 + 锡 0.1 → 0.05 青铜/秒）

// 记录系统（本代核心）
recorded: string[];        // 已刻录科技 id（槽位占用 = recorded.length）
recordedOnce: string[];    // 历史上刻录过的科技 id（供档案库加成计数；与技术退役解耦）

// 贸易系统
localOre: 'copper' | 'tin' | 'alluvial';   // 本地矿藏（决定铜/锡自给）
tradeRoutes: TradeRoute[];                 // 已建立的路线
reputation: number;                        // 声望 0–100，初始 50
```

```ts
interface TradeRoute {
  partnerId: string;        // 邻邦 id（数据驱动，首版 5 个固定）
  demand: ResourceId;       // 我方支付的货物
  supply: ResourceId;       // 我方换得的货物
  distance: 1 | 2 | 3;      // 距离系数 = 1 + 0.15 × 距离
  cycleAccum: number;       // 商队周期计时（30 秒一轮）
  priceHistory: number[];   // 近 5 周期价格（供迷你折线图与需求冲击计算）
  contractUntil?: number;   // 契约锁价的截止时间戳
}
```

### 7.2 引擎新增函数（签名与公式）

| 函数 | 公式 / 行为 | 边界情况 |
|---|---|---|
| `getRecordCapacity(state)` | `3 + 学宫×5 + 泥板制作加成(2) + 档案库扩建(0)` | 返回 `{cap, used, free}` |
| `canRecord(techId, state)` | ① `used < cap` ② `knowledge ≥ cost×0.1` ③ `jobs.scribe ≥ 1` | reason 必须可显示：「槽位已满 / 知识不足 / 无书吏」 |
| `recordTech(techId, state)` | 扣 `cost×0.1` 知识；`recorded.push(id)`；**不可撤销** | 已刻录过的拒绝（幂等） |
| `getTechEffectMul(state, techId)` | 口头 `×0.5`；已刻录 `×1.0`；再叠 `eraDecay(d)` | 与现有 `aggregateEffects` 的乘法链合并 |
| `calcKnowledgeOutput(state)` | `书吏数 × 0.15 × (1 + 书吏训练 0.3 + 六十进制 0.2)` | 需 `jobs.scribe ≥ 1` 且有空槽（设计：无槽则无产出？⚠️ 待拍板，见 §8） |
| `tickTrade(state, dt)` | 30 秒一轮（见 7.3） | 书吏不足 → 路线效率从 1.0 向 0.3 线性下滑 |
| `getTradePrice(good, route, state)` | `基准价 × 距离系数 × 需求冲击 × 随机波动(0.8–1.2)` × 声望修正 × 契约锁定 | 未研究度量衡 → `×0.85`（15% 换算损耗） |
| `getReputationEffect(rep)` | `≥70 → 全线 −10%`；`≤20 → 全线 +25% 且 20% 概率拒交` | 声望变化只来自契约/毁约（首版无其他来源） |
| `applyJobUpgrade`（已有） | E3 无新增进阶对，但**织工若取消**则走退役路径 | 退役人数回闲置池，不掉人口 |
| `calcJobOutput`（改） | E3 起：`unitOutput × N^0.9 × 各倍率` | **必须 era 门控**：E1/E2 保持线性 |

### 7.3 `doTick` 的执行顺序（重要：顺序错会算错账）

```
1  资源产出（含 N^0.9、季节、冶炼投料）
2  资源消耗（人口吃粮 0.2/s/人；冶炼吃铜锡）
3  贸易结算（累积 30 秒触发一轮；只动 copper/tin/food/wood/stone/lapis）
4  人口增长（r × P × (1−P/K) × 三因子；K = 320 + 民居×130）
5  知识产出（书吏）
6  记录/刻录（玩家手动，tick 不自动刻）
7  消息与统计
```

> ⚠️ **为什么贸易排在人口之前**：贸易换回的粮食要**计入本 tick 的食物池**之后才结算人口增长，
> 否则"粮食断供 → 贸易救回来"会晚一拍体现，玩家会看到莫名其妙的人口下跌。
> （E2 曾因执行顺序导致过类似的失真，见 `autoplay` 的踩坑记录。）

## 八、待拍板 4 项 · 推荐方案

> 每项给推荐与理由。**你只需回"按推荐"或指出要改哪条**，不用逐条写方案。

### 8.1 织工与织物的去留 → **推荐：取消织工岗位，织物转为贸易出口品**

- 理由：织物至今**没有任何消费方**（挂了两个版本的死资源）；E3 的贸易系统恰好给了它一个出口——
  有库存就能按基准价卖出，不需要岗位继续产出。
- 做法：`jobs.ts` 给织工声明退役（无进阶目标，人数回闲置池）；织物从"岗位产出"改为"库存品"。
- 备选：保留织工并把织物做成 E3 的"舒适度"输入——但舒适度机制 E2 就该有，现在补属于新范围，不建议在这代做。

### 8.2 本地矿藏 → **推荐：首版固定「冲积平原」（铜锡全靠进口）**

- 理由：① 最贴合苏美尔主线（设计文档的史实依据就在这）；② **强制贸易系统被使用**——
  E3 的核心矛盾只有在"本地无矿"时才成立；③ 首版少一条分支，配平面小。
- 铜矿带 / 锡矿带留给 **P2 平行文明的起源选项**（正好与"河谷/草原/海洋"三起源的扩展方向一致）。

### 8.3 贸易邻邦 → **推荐：固定 5 个邻邦，数据写死在 `e3-trade.ts`**

- 理由：可测试（`autoplay e3` 的回归才稳定）、可配平（价格浮动是随机的，但**结构**必须确定）。
- 随机化留给重玩层（P2 解锁后），首版不做。

### 8.4 「经验」字段 → **推荐：保留字段、E3 起停止产出、数值不清零**

- 理由：清零违反"文明积累不清零"（你已拍板）；而 E3 关闭经验产出通道是设计文档的明文规则
  （研究货币换成书吏的「知识」）。保留字段 = 旧存档零风险，未来 E4 若要"经验与知识合流"也留了口子。
