# 经济与数值成长系统规划

> **状态**：规划定稿，暂不实施
> **范围**：E1-E8 的资源、人口、职业、建筑、科技和存储成长
> **当前约束**：本阶段只更新设计文档，不修改 `demo/src` 生产代码。
> **关联文档**：[核心循环](./01-core-loop.md)、[科技发展计划](./02-tech-eras.md)、[存储规划](./storage-plan.md)、[E2 设计](./eras/E2-sedentary.md)、[E3 设计](./eras/E3-citystate.md)、[AI 设计与交付规范](../AI-DESIGN-RULES.md)

## 1. 目标与问题定义

本规划解决两类长期问题：

1. 建筑建造数量增加后仍按固定成本购买，导致“无限复制同一座建筑”成为最优解。
2. 职业者数量变化后，产出要么机械地统一递减，要么完全不受工作位、原料、环境和人口机会成本约束。

数值系统的目标不是让所有曲线都变复杂，而是让每个增长结果都能回答三个问题：

- 玩家投入了什么：人口、建筑、资源、科技或时间。
- 玩家突破了什么瓶颈：环境、工位、原料、运输、存储或机会成本。
- 玩家付出了什么代价：递增建造成本、维护消耗、占用人口或风险。

### 1.1 设计结论

- **普通职业者默认线性产出**，不统一套用边际收益。
- **猎人保留环境边际收益**，因为猎场是有限且会被多人共享的外部资源。
- 其他职业只在拥有明确瓶颈时使用限制函数；限制来自系统语义，不来自“为了压制数值”而添加。
- **建筑成本使用按类型分层的蠕变曲线**，但必须设置可解释的软上限，避免指数成本失控。
- E1/E2 已有配平是回归基线；E3 及以后不能通过悄悄改变旧时代公式来解决新问题。

## 2. 统一资源流模型

所有生产和成长结果都遵循同一条数据流：

```text
人口
  -> 可用劳动力
  -> 职业分配
  -> 工位 / 环境 / 原料 / 运输约束
  -> 基础产出
  -> 科技 / 建筑 / 季节 / 时代修正
  -> 资源扣除、存储截断、维护和事件
  -> 最终资源变化
```

推荐的通用表达式：

```text
finalOutput =
  baseOutput(count, context)
  * technologyMultiplier
  * buildingMultiplier
  * seasonMultiplier
  * eraMultiplier
  * resourceAvailabilityFactor
  * routeOrEnvironmentFactor
```

约束必须先于产出结算：

1. 计算人口可用量和岗位人数。
2. 将岗位人数限制到建筑工位、环境容量或路线容量。
3. 计算基础产出或边际曲线。
4. 乘科技、建筑、季节和时代效果。
5. 扣除投入资源与维护。
6. 应用存储上限、溢出损失和结构化事件。

禁止在后续步骤重新覆盖已经计算过的产出；每个倍率只能在明确的结算阶段进入一次。

## 3. 建筑成本蠕变

### 3.1 基础公式

同一建筑已拥有 `n` 座时，下一座建筑成本为：

```text
cost(n) = ceil(baseCost * growth^n * eraMultiplier * techMultiplier)
```

约定：

- 第一座建筑使用 `n = 0`，成本等于基础成本。
- 第二座建筑使用 `n = 1`。
- `n` 只统计同一 `BuildingId` 的已建数量，不把不同建筑混在一起。
- 各资源分别向上取整；不能因为某项资源很小而变成零成本。
- 科技折扣不能绕过时代门控，也不能把最终成本降到基础成本以下，除非设计明确声明为替代材料。

现有 `getBuildingCost()` 已有幂函数入口，后续实现优先复用该入口，先补齐数据配置和测试，不新增第二套成本计算。

### 3.2 建筑类型倍率建议

| 类型 | 代表建筑 | `growth` 建议区间 | 设计理由 |
|---|---|---:|---|
| 人口建筑 | 住所、村落民居、城市住宅 | 1.12-1.18 | 土地、管理和公共服务压力逐步增加 |
| 生产建筑 | 田地、作坊、窑、熔炉 | 1.16-1.24 | 资源点、维护和组织成本随规模增加 |
| 存储建筑 | 粮仓、仓库、国库、料场 | 1.10-1.16 | 扩容应稳定可追赶，不能成为纯惩罚 |
| 网络建筑 | 商栈、道路、港口、通信设施 | 1.18-1.28 | 网络节点越多，维护和协调成本越高 |
| 战略建筑 | 学宫、城墙、军团、数据中心 | 1.22-1.32 | 代表稀缺的高等级组织能力 |

这些区间是首轮配平起点，不是硬编码结论。每座建筑必须在设计表中填写成本类别、倍率、收益类型、容量上限和维护说明。

### 3.3 软上限与可玩性保护

纯指数成本在高数量时会爆炸，因此采用“前段蠕变、后段软封顶”的实现目标：

```text
rawCost(n) = baseCost * growth^n
effectiveCost(n) = baseCost + (rawCost(n) - baseCost) * softCapFactor(n)
```

首轮实现可以先使用分段倍率，不要求一次引入复杂函数：

- 1-5 座：完整倍率，体现早期选择。
- 6-12 座：倍率增长放缓，保证中期仍可扩张。
- 13 座以后：由人口、维护、工位或资源点成为主要限制，成本不再无限膨胀。

每类建筑至少验算第 1、2、5、10 座成本，并检查第 10 座是否仍有合理的建设目标。

### 3.4 建筑收益原则

- 成本递增不等于收益递减；如果建筑已经受工位或人口约束，收益可以保持稳定。
- 同一建筑的收益必须能解释其增长成本：容量建筑增加容量，生产建筑增加工位或转化能力，网络建筑增加路线或运力。
- 同时提供容量和生产倍率的建筑必须拆开显示来源，避免玩家无法判断“多造一座到底解决了什么”。
- 建筑维护若存在，必须单独列出，不要把维护偷偷混入产出倍率。

## 4. 职业产出分类

### 4.1 A 类：普通线性职业

适用于伐木者、打石者、普通农夫、普通书吏等，前提是其资源来源和设施容量已经由其他机制表达：

```text
output = workers * unitOutput * multipliers
```

线性不是无约束。约束应落在“能分配多少人”“有多少工位”“是否有投入资源”和“人口机会成本”上，而不是给每个人偷偷降低效率。

### 4.2 B 类：环境型职业

猎人属于环境型职业。猎场是共享且有限的，人数增加会竞争同一环境资源，使用饱和曲线：

```text
huntingOutput = habitatCapacity * (1 - exp(-hunters / habitatTau))
```

注意：猎人总产出可以边际递减，但工具科技、猎场质量和迁徙事件仍可作为独立倍率进入。UI 必须显示“猎场容量”和“当前利用率”，不能只显示一个模糊的低效率提示。

### 4.3 C 类：工位型职业

农夫、牧人等依赖设施工作位：

```text
effectiveWorkers = min(assignedWorkers, availableWorkslots)
output = effectiveWorkers * unitOutput * seasonMultiplier * techMultiplier
```

- 每块田地提供固定农夫工作位；超过工作位的人必须回到待命人口或其他岗位。
- 牧人受畜栏容量和饲料供给共同限制。
- 建筑未被实际工作者使用时，不能同时提供完整的生产能力和人口承载力，除非设计明确区分二者。

### 4.4 D 类：投入型职业

冶炼工不是单纯的“青铜生产者”，而是铜和锡的转化者。

```text
requestedInput = workers * recipeInputPerWorker
inputFactor = min(availableCopper / requestedCopper, availableTin / requestedTin, 1)
output = workers * unitOutput * inputFactor * furnaceMultiplier
actualInput = requestedInput * inputFactor
```

缺一种原料时按比例降速；不得消耗完整配方却产出零，也不得凭空补齐稀缺材料。UI 需要显示当前瓶颈是铜、锡还是熔炉工位。

### 4.5 E 类：网络型职业

商人的产出由路线、运力、距离、契约和书吏支持共同决定：

```text
routeCapacity = merchants * transportOutput / distanceFactor
tradeOutput = min(routeCapacity, partnerSupply, localStorageRoom)
```

路线数量增加后，书吏、维护和中断风险应成为约束。距离提高运输成本或降低有效运力，但不应通过隐藏倍率让玩家无法理解交易结果。

### 4.6 F 类：机会成本型职业

书吏可以保持线性知识产出：

```text
knowledge = scribes * knowledgePerScribe * writingMultiplier
```

其约束不使用统一的 `N^0.9`，而来自：

- 书吏占用人口，减少可用于农业、采矿和冶炼的劳动力。
- 记录容量和空闲泥板槽位限制可执行的记录行为。
- 活跃贸易路线消耗账目维护能力。
- 知识是研究货币，科技成本和刻录成本形成长期消耗。

这样“多养书吏”仍然有代价，但玩家能看见代价来自哪里。

## 5. 关于规模递减的统一决策

现有 E3 草案中的通用 `N^0.9` 不再作为职业系统默认规则。后续改为**声明式边际模型**：

```text
scalingModel: 'linear' | 'environmentSaturation' | 'workslotLimited' | 'inputLimited' | 'networkLimited'
```

规则：

- 默认值为 `linear`。
- 只有数据明确声明为环境型或设施型时，才使用非线性模型。
- 一个职业只能有一个主规模模型；科技、建筑、季节是额外倍率，不能重复作为规模模型。
- E1/E2 维持既有线性基线，猎人已有的独立环境饱和曲线除外。
- E3 普通职业不自动套 `N^0.9`；猎人、农夫、牧人、冶炼工、商人、书吏分别按第 4 节模型处理。

## 6. 人口与机会成本

人口不是单纯的产出倍率，而是所有职业的共享预算：

```text
population = assignedWorkers + idlePopulation + dependents
```

验算重点：

- 书吏增加后，知识增长应上升，但食物、木材、石头或金属的机会成本也应可观察。
- 猎人增加后，前几名猎人收益明显，继续增加逐步接近猎场上限。
- 农夫增加超过田地工位时，粮食不会继续无条件线性增长。
- 牧人增加超过畜栏或饲料能力时，新增牧人不能制造免费牲畜。
- 人口接近住房承载力时，人口增长放缓；缺粮时先影响增长，储备耗尽才进入减员。

## 7. 存储与成长曲线的关系

成本蠕变和存储规划必须一起配平：

- 资源产量增加后，存储容量必须有同步扩张路径。
- 存储建筑自身也使用蠕变成本，但其成本增长不应快过它解决的容量问题。
- 木材、石头和主粮等跨代基础资源容量必须随时代单调递增。
- 时代资源进入下一时代后，必须明确是继续存储、转化为基础资源，还是作为历史库存保留。
- 溢出、腐败、换算损耗和维护损失要分别显示，不能合并成一个“资源消失”。

## 8. E1-E3 迁移策略

### P0：只读审计与基线记录

- 记录现有建筑成本、职业单位产出、工位、资源上限、E1/E2 通关时间和 E3 起始状态。
- 列出每个公式的输入、输出和时代门控。
- 不修改代码，不接受“顺便修复”的无关变更。

### P1：冻结统一数据契约

- 为建筑补齐成本类别、倍率、维护和收益类型。
- 为职业补齐 `scalingModel`、单位产出、工作位、环境、配方或路线依赖。
- 统一产出结算顺序，确认科技和建筑倍率不会被后续分支覆盖。

### P2：建筑成本曲线

- 先对 E3 建筑启用分类型蠕变。
- 用第 1、2、5、10 座验算成本，确认学宫、商栈、仓库等关键设施仍可达。
- 再评估是否将同一框架回填 E2；任何影响 E1/E2 基线的变更必须单独提交和回归。

### P3：职业模型迁移

- 普通职业恢复或保持线性。
- 猎人保留环境饱和。
- 农夫、牧人接入工位和容量；冶炼工接入比例配方；商人接入路线容量；书吏保持线性并承担机会成本。
- 移除 E3 对普通职业的通用 `N^0.9` 依赖后，重新配平科技和时代门槛。

### P4：E3 配平

- 以“楔形文字可达”为首要路径：首项科技不能依赖尚未解锁的书吏产出或记录容量。
- 验证经验在 E3 的显示名称与研究货币规则，不新增并行 `knowledge` 状态解决同一语义问题。
- 验证铜、锡、青铜链和贸易路线能在有限人口下同时启动。
- 验证仓库、学宫、商栈的蠕变成本不会阻塞 E3 到 E4 的交接。

### P5：回归与文档同步

- 先跑 E1/E2 守门回归，再跑 E3 可达性和长时间模拟。
- 将最终数值回写 E2/E3 设计文档、存储规划和开发清单。
- 只有代码、测试和文档三者一致后，才允许进入下一代实施。

## 9. 配平验收矩阵

每次改动至少记录以下结果；结果应能由纯函数或可复现模拟得到。

| 场景 | 必须观察的结果 | 通过标准 |
|---|---|---|
| 建第 1/2/5/10 座同类建筑 | 各资源成本与累计成本 | 成本递增、无零成本、关键建筑仍可达 |
| 5/10/20 名伐木者或打石者 | 产出曲线 | 保持线性，倍率来源可解释 |
| 1-20 名猎人 | 总产出和人均产出 | 总产出趋近猎场容量，人均逐步下降 |
| 农夫超过田地工位 | 有效工作人数 | 超出工位者不产生额外农业产出 |
| 牧人超过畜栏或饲料 | 有效牲畜产出 | 受容量或饲料较小者限制 |
| 缺铜或缺锡冶炼 | 实际投入和青铜产出 | 按比例降速，UI 指出具体缺料 |
| 1/2/3 条贸易路线 | 运力、书吏和价格 | 距离与路线维护可见，不能凭空进口 |
| 书吏从 0 增至 20 | 知识与物资机会成本 | 知识线性上升，生产岗位减少可解释 |
| E1/E2 基线 | 通关时间和首屏 | 与已冻结基线一致，或有单独批准的基线变更记录 |
| E3→E4 交接 | 资源、建筑、科技状态 | 目标条件完整可达，未出现隐形死锁 |

## 10. 测试规划（实施时执行）

本文件只规定测试范围，不在规划阶段添加测试代码。实施阶段必须覆盖：

1. **纯函数测试**：成本曲线、每类职业模型、工位裁剪、配方比例、存储容量、资源显隐和科技前置。
2. **tick 测试**：生产顺序、原料扣除、贸易结算、人口消耗、季节变化、溢出和事件反馈。
3. **可达性测试**：从真实起始状态跑到楔形文字、青铜、钢铁和 E3→E4 条件，不能直接构造目标状态代替路径。
4. **基线测试**：E1/E2 的 autoplay、SSR 首屏和关键中期状态；新规则必须时代门控。
5. **长时模拟**：至少模拟 1 小时在线和 8 小时离线，检查资源是否无穷增长、成本是否溢出、人口是否异常崩溃。
6. **构建检查**：`npm run regression`、TypeScript 检查、Vite 构建和 `git diff --check`。

## 12. 结论

本系统采用“**建筑成本蠕变 + 职业模型分类 + 明确瓶颈 + 线性默认**”的组合：

- 建筑越多，材料、土地和管理成本越高。
- 普通职业者不会因为人数增加而被统一处罚。
- 猎人按有限猎场自然饱和。
- 农夫和牧人受工作位、畜栏和饲料约束。
- 冶炼工受铜锡比例约束。
- 商人受路线、距离、运力和书吏支持约束。
- 书吏保持线性知识产出，但通过人口机会成本和记录系统承担代价。

这样数值成长服务于每个时代的核心玩法，而不是把所有系统压成一条看不见的 `N^0.9` 曲线。
