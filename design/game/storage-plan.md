## 二、三条元规则（跨时代不变，本文件的核心）

> **规则 1 · 每代必有存储**：每个时代的**建筑集或科技树里必须至少有一项"扩容"手段**。
> 理由：产出若无处安放，生产即无意义。**没有存储的时代无法通关**——它会在跃迁门槛前被自己的产量卡死。

> **规则 2 · 基础资源容量单调递增**（你本次明确要求的规则）：
> **木材、石头、主粮**这三类跨代继承的实体资源，其容量上限**必须随时代单调递增**，且**必须由本时代的手段驱动**（建筑或科技），不允许是全局硬编码常量。
> 禁止出现：跨了三代，木材上限仍是 500。

> **规则 3 · 形态差异化，动词不变**：每一代换的是"**存什么 + 拿什么装 + 存不住会怎样**"（形态），
> 不改的是"**扩上限**"（动词）。这保证了铁律 1（每代必须引入新动词）在存储线上的表达是**"新形态"而非"新数字"**。

## 三、存储的三个维度（每代都要能填满）

| 维度 | 回答的问题 | 每代表现 |
|---|---|---|
| **容量 Cap** | 能装多少 | 由**存储建筑 + 存储科技**决定 |
| **保真 Fidelity** | 装进去会不会坏 | 腐败 / 蒸发 / 贬值 / 溢出——**这是"形式差异"的主要来源** |
| **专精 Specialty** | 本代特有的"存货"是什么 | 活体储备（E2）、泥板槽位（E3）、典籍（E5）、煤（E6）、数据（E7） |

**"形式差异"落在保真维度上，而不是容量维度上**——这正是你说的"在某些特定物品的存储上有一点点区别"，
而"基础资源容量都在扩张"则落在容量维度上。两个维度分工明确，互不干扰。

### 资源的三分法（先定义清楚，后面所有表都按这个口径）

| 类别 | 定义 | 成员 | 存储规则 |
|---|---|---|---|
| **基础资源** | 跨代继承、每代都要用的实体资源 | 木材 🪵、石头 🪨、主粮（**统一为「食物」**，2026-09-12 起谷物已并入） | **容量必须逐代单调递增**（规则 2） |
| **时代资源** | 只在一两个时代活跃的资源 | 铜/锡/青铜（E3）、铁/铸币（E4）、纸张/典籍/白银（E5）、煤/钢/电/工业品（E6）、数据/铀（E7） | 由本代**存储建筑**提供容量；**继承时按规则 2 并入基础资源** |
| **状态仪表盘** | 不可存储的独立数值 | 火种、秩序、识字率、蒸汽压力、算力、堆芯风险 | **不参与存储**，只作为"看板" |

> **一个刻意的边界**：**经验 / 知识 / 研究点不设容量上限**。它们是科技货币，卡上限会让"研究队列"这种挂机机制瘫痪。存储只约束**实体资源**。

## 四、通用规则：存储建筑必须"双扩容"

> **这是本文件最重要的一条可执行规则。**
>
> 每个时代的**存储建筑（Storage Building）必须同时提供两种效果**：
>
> ① **专精容量** —— 本代的核心存货（食物（原谷物）/ 典籍 / 煤 / 数据……）
> ② **基础容量** —— 木材、石头、主粮等**继承资源的上限提升**
>
> 因此"建一座仓库"永远同时回答两个问题：**"存得下本代的新东西"** 与 **"存得下跨代的老资源"**。

这条规则一次性解决三个问题：

- **解决断链**：木材/石头不再写死，而是随"你建了几个仓库"一起长。
- **解决节奏**：玩家每代都必须至少建一座存储建筑，**存储自动成为每代的固定节奏点**，不需要额外造一个系统去推。
- **解决可解释性**：鼠标悬停仓库 → "食物 +800 / 木材 +300 / 石头 +300"，来源一目了然（满足铁律 6）。

### 双扩容的两种落地形态

| 形态 | 做法 | 适用 |
|---|---|---|
| **A · 单一建筑双效** | 一个建筑同时给专精容量 + 基础容量 | E2 粮仓、E5 图书馆、E6 料场、E7 数据中心 |
| **B · 建筑 + 科技分工** | 建筑给专精容量，配套科技给基础容量倍率 | E3（学宫 + 窖藏粮仓）、E4（国库 + 仓储法） |

> **为什么允许两种形态**：不是每个时代都适合"一个建筑包打天下"。E3/E4 的玩法重心在贸易与治理，
> 存储建筑不宜喧宾夺主，因此用"建筑管专精、科技管基础"的分工形态，**保持存储是配角但不缺席**。

## 五、基础资源容量阶梯（跨代单调递增 · 草案）

**锚定方法**：每一代的基础容量必须 **≥ 下一代起始状态所需的资源量**，否则玩家在跃迁瞬间就会溢出损失。
（"下一代起始"列取自各时代文档 §11.1。）

| 时代 | 木材上限 | 石头上限 | 主粮上限 | 下一代起始（锚点） | 是否装得下 | 扩张来源 |
|---|---|---|---|---|---|---|
| **E1** | 500 | 500 | 1,000 → **2,000**（烟熏 ×2） | — | — | 科技「烟熏储存」（**已实现**） |
| **E2** | 500 → **800** | 500 → **800** | 主粮 `1000（E1 基础）+ 400 + 800×粮仓` | E3：木 800 / 石 600 / 食 2,000 | ✅ 恰好 | **粮仓双效（已实现）** |
| **E3** | **3,000** | **3,000** | **6,000** | E4：木 3,000 / 粮 5,000 | ✅ 恰好 / ✅ | 窖藏粮仓 + 仓储科技 |
| **E4** | **9,000** | **9,000** | **15,000** | E5：木 2,000 / 石 1,500 / 食 3,000 / 铁 800 | ✅ | 国库（双效）+ 仓储法 |
| **E5** | **24,000** | **24,000** | **40,000** | E6：木 6,000 / 石 5,000 / 食 8,000 | ✅ | 图书馆（双效） |
| **E6** | **60,000** | **60,000** | **100,000** | E7：食 5,000 / 钢 1,200 | ✅ | 料场（双效）+ 煤矿 |
| **E7** | **150,000** | **150,000** | **250,000** | E8：待 E8 文档定稿 | — | 数据中心（双效） |
| **E8** | **400,000** 量级 | **400,000** 量级 | **600,000** 量级 | — | — | 星际货舱 / 物质压缩 |

**递推系数 ≈ ×2.5 / 代**（E3→E7：3,000 → 9,000 → 24,000 → 60,000 → 150,000，比值 3.0 / 2.67 / 2.5 / 2.5）。

> **E2 的 800 是"1 座粮仓"的结果，不是天花板**：粮仓双效给出 `500 + 300×N`，
> 因此 E2 玩家**建得越多，木/石上限越高**——这正好把"扩仓"从"只为过冬"变成"顺带扩张基础容量"，
> 是规则 4 在 E2 的具体收益。
>
> **时代资源并入基础资源**：E4 的「铁」在 E5 起按规则 2 **并入基础资源**（E5 起始铁 800 即由 E4 仓库带出），
> 此后各代的门槛必须同时纳入铁/钢/工业品等**已并入的旧时代资源**，本表为便于阅读只列木/石/主粮三项。

> ⚠️ **除 E1 / E2 的既有值外，上表全部为「首轮草案」**，须随各时代配平定稿校准。
> **但"单调递增"这一性质本身是铁律，不随数值调整而改变。**

> 📌 **E1 的例外**：E1 是**冻结的回归基准**（beeline 1163s + 首屏逐字节一致），
> 因此 **本次不给 E1 增加存储建筑或科技**。木材/石头在 E1 保持 500 —— 在 E1 的最高成本 40 石的尺度下够用。
> 若未来要给 E1 补木石扩容，**必须单独立项并重跑全部回归**（见第九节）。

## 七、逐时代详解

### E1 · 蒙昧 —— 地窖与火种

- **形态**：旧石器的存储是**坑穴（pit/cache）**——挖一个坑，垫上兽皮或草，埋起来。
- **专精存储**：**火种**。它不可存储，只能"维持"——所以 E1 的存储主题实际上是"**存燃料**"（木材既盖房又维持火种）。
- **基础容量**：食物 `1,000 × 2 = 2,000`（科技「烟熏储存」）。
- **保真**：**腐败**。食物随时间按比例损失（未实现；烟熏储存的作用被简化成了纯容量翻倍）。
- **史实锚点**：纳图夫文化（Natufian，约 12,500–9,500 BC）已有**石砌/抹泥的储藏坑**；上旧石器时代晚期的窖藏坑（cache pits）是定居前的存储证据。
  ⚠️ 具体年代与遗址分布**未逐一核实**，标记待核。
- **本次动作**：**不改**（保护 932s 基准与首屏逐字节一致，见第五节的 E1 例外）。

### E2 · 定居 —— 粮仓与陶罐

- **形态**：**土坯粮仓 + 陶罐**。E2 的核心机制已把"存储"当作主角（`E2-sedentary.md` §2：粮仓上限 = 文明能撑过几个冬天）。
- **专精存储**：
  - **活体储备（牲畜）** —— 已实现，**不占粮仓容量**，等于一座"免费的隐形粮仓"（E2 文档 §3）。
  - **陶窑** —— 已实现，`+15%` 食物上限 ×最多 3 座，**语义是"储藏质量"而非"仓库变大"**。
- **基础容量**：⚠️ **缺口**。木/石目前硬编码 500，需按规则 2 补上 E2 的扩张。
  **建议方案**：让「粮仓」承担**双扩容**——`食物 +800 / 木材 +300 / 石头 +300`。
  这样 **E2 建 1 座粮仓 → 木/石上限 800**，正好等于 **E3 的起始木材 800**，断链自然接上；
  建筑总数仍为 5 座（不违反"新增 3–6 座"）。
- **保真**：**季节溢出 + 冬季缺口**（已实现"溢出浪费"，未实现损耗率）；
  规划中的**食物腐败 / 储藏损耗**（见 `seasons-plan.md` §3.3）应挂在**陶窑 / 粮仓 / 陶罐**三者上——**E2 就是它的正确落脚点**。
- **史实锚点**：约旦河谷 Dhra' 遗址发现**距今 11,000 年的前驯化期粮仓**（PNAS 2009）；PPNA 定居点"almost every settlement contained storage bins made of either stones or mud-brick"。

### E3 · 城邦 —— 仓廪与泥板库

- **形态**：存储第一次**分裂成两条线**——**物质**（粮仓）与**信息**（泥板）。
  这是 E3 与前面所有时代的根本区别：**"存东西"之外，出现了"存记录"**。
- **载体建筑**：
  - **学宫（é.dub.ba）** —— 已设计，**记录容量 +5 / 座**（本代核心仪表盘）。
  - **粮仓** —— 需从 E2 的"主粮专仓"升级为**仓廪**（多品类）。
- **专精存储**：**记录容量（泥板槽位）**。已设计为独立仪表盘，3 – 3+5N。
- **基础容量**：木/石/食 → **3,000 级**（草案）。扩张来源：**科技「窖藏粮仓」（已设计，食物储备上限 +100%）** + 新增仓储科技。
- **保真**：**换算损耗**。已设计「标准器」（全城换算损耗 −5%）与「度量衡」科技——**这本质上就是"交易仓储中的度量损耗"**，是存储保真维度在贸易上的投影。
- **史实锚点**：苏美尔神庙经济以**粮仓**为核心结算单位；Ebla（约 2350 BC）出土约 1,800 块泥板 + 4,700 块残片；Kültepe/Kaneš 的 kārum 遗址出土 **23,500 块楔形文字泥板**（约 1945–1835 BC），是古代近东最大的私人文书收藏。

### E4 · 帝国 —— 国库与驰道仓

- **形态**：从"仓库"升级为"**国库**"——存储第一次与**财政**绑定。存的不只是粮，还有**钱**。
- **载体建筑**：⚠️ **缺口**——E4 现有六座建筑（官署 / 驰道 / 铸币厂 / 营垒 / 住宅 / 法典碑）**没有任何一座是存储建筑**。
  **建议新增「🏛️ 国库」**（或复用"官署"增设仓储等级）：`粮 + 木 + 石 基础容量提升；铸币上限`。这是 E4 唯一缺失的方向。
- **专精存储**：**秩序**（仪表盘，不参与存储）。
- **基础容量**：木/石/粮 → **9,000 级**（草案）。
- **保真**：**铸币贬值 + 粮仓霉变**。E4 的存储首次出现"**存着会变少**"的财政含义——这是"铁器帝国"与"青铜城邦"在存储手感上的分水岭。
- **史实锚点**：罗马 **horrea**（粮仓）是帝国后勤的骨架，Ostia 的 Horrea Galbae 常引约 140 个仓间；罗马国库 **aerarium** 设于萨图恩神庙，后设 **fiscus** 为元首私库。

### E5 · 觉醒 —— 图书馆与书库

- **形态**：存储第一次成为**知识的基础设施**。E5 文档已把"存储"列为印刷链**四个瓶颈之一**（原料 / 产能 / 转化 / **存储**）。
- **载体建筑**：**📚 图书馆** —— 已设计，**典籍存储上限 +20,000；研究速度 +5%**。
  按**规则 4（双扩容）**，图书馆还应提供**基础容量扩张**（木/石/食 → 24,000 级）。
- **专精存储**：**典籍 = 储蓄**。E5 文档的措辞很精确："典籍库存 = 储蓄；学者数 = 提现速度"——**存储第一次成了一个可"提现"的账户**。
  ⚠️ 注意：里程碑门槛是**累计产量**而非当前库存，所以"被读掉的典籍同样计入"。
- **基础容量**：木/石/食 → **24,000 级**（草案）。
- **保真**：**虫蛀 + 溢出**。已设计科技「公共图书馆」（典籍存储上限 +50%）——对应"更专业的保管"。
- **史实锚点**：Biblioteca Marciana（威尼斯，1468）；梵蒂冈图书馆（1475）；印刷术使书价降约 4/5，**藏书量第一次超过个人记忆的容量**。

### E6 · 机器 —— 煤仓与料场

- **形态**：存储第一次成为**能量链的前置**。煤存不下 → 锅炉没燃料 → 压力崩 → 全厂停摆。
- **载体建筑**：
  - **⛏️ 煤矿** —— 已设计，`煤产能 +25% / 座；煤存储上限 +20,000 / 座`。**已是"产能 + 存储"双效，符合规则 4**。
  - ⚠️ **缺口**：没有一座建筑扩**木/石/工业品/钢**的容量。**建议新增「🏗️ 料场」**（双效：基础容量 + 工业品上限）。
- **专精存储**：**蒸汽压力**（仪表盘）；**煤 + 钢**（实体，可存储）。
- **基础容量**：木/石/食 → **60,000 级**（草案）。
- **保真**：**煤自燃 / 积压**。堆煤会自燃是真实工业事故，可作为 E6 的"存储有代价"表达——**存太多反而危险**，这是与前面所有时代都不同的存储张力。
- **史实锚点**：英国煤产量约 3 Mt（1700）→ 超过 30 Mt（1830）→ 236 M 短吨（1905）；产量峰值 1913 年 287 Mt。**煤的存储规模与产量同步膨胀**，正是"基础容量必须扩张"的史实注脚。

### E7 · 电子 —— 数据中心与磁芯

- **形态**：存储第一次变成**数字的**。E7 的文献里，存储技术已经是一条明线：
  **磁芯存储（1953）→ 磁盘存储（1956）→ 数据库（1970）**，分别给 `算力 +10% / 数据上限 +40% / 数据上限 +50%`。
- **载体建筑**：⚠️ **缺口**——E7 六座建筑（计算中心 / 冷却塔 / 核电站 / 网络节点 / 发射场 / 城市住宅区）**没有存储建筑**。
  **建议新增「🗄️ 数据中心」**（双效：**数据上限 + 基础容量**）。
- **专精存储**：**数据 + 算力**。E7 文档的区分极为关键——**"数据是'花的'，算力是'占的'"**：
  数据一次性花掉买自动化；算力被自动化持续占用。**所以"存得下"（数据）与"跑得动"（算力）是两件事** —— 这是存储维度在信息时代的精确投影。
- **基础容量**：木/石/食 → **150,000 级**（草案）。
- **保真**：**介质失效 / 数据损坏**。E7 已有「维护技师」（每 1 人覆盖 10 台计算机）——**它天然就是"数据保真"的人力成本**。
- **史实锚点**：MIT Whirlwind 磁芯存储（1953）；IBM 305 RAMAC（1956）首创磁盘存储，容量 **5 MB**；Codd 关系模型（1970）使"数据库"成为独立的存储范式。

### E8 · 星海 —— 星际货舱与物质压缩

- **形态**：⚠️ **待设计**——`design/game/eras/` 下**没有 E8 文档**，存储线目前**断在 E7**。
- **草案方向**：从"单一仓库"变为**多星球并行仓储**——每颗星球有独立库存，存储的决策从"建多大"变成"**放在哪颗星球**"。
  这与 E8 的核心动词（殖民·改造）一致：**存储的最终形态是"分布式"的**。
- **基础容量**：×300 量级（草案）。
- **保真**：**真空泄漏 / 辐射**（纯推测，须待 E8 文档定稿）。

## 八、数据结构草案（供未来实施参考，本文件不实现）

目标是把 `getResourceStorage` 里的 `switch` + 硬编码常量，改为**按时代注册的数据表**：

```ts
/** 存储档案：描述"一个时代怎么存东西" */
export interface StorageProfile {
  eraId: EraId;
  /** 基础资源容量基准（木/石/主粮），随时代单调递增 */
  baseCap: { wood: number; stone: number; staple: number };
  /** 存储建筑的基础容量加成（双扩容的②） */
  storageBuildingBonus: { wood: number; stone: number; staple: number };
  /** 保真：每秒损耗率（0 = 不损耗），可被科技下调 */
  decayPerSec: Partial<Record<ResourceId, number>>;
  /** 该代特有的专精存储键（如 'grain' | 'scroll' | 'coal' | 'data'） */
  specialty?: ResourceId;
}

/** 按时代索引；未注册的时代回落到"继承上一代" */
export const STORAGE_PROFILES: Record<EraId, StorageProfile>;
```

**迁移原则**：

1. `getResourceStorage('food'/'wood'/'stone'/'grain')` 改为读档案，**E1 / E2 的返回值必须逐位相等**才允许合入
   （E1：food `1000×mult`、wood/stone `500`；E2：grain `(400+800N)×(1+…)`）。
2. 存储建筑通过**效果位**（而非直接读建筑）提供加成，接入现有 `aggregateEffects` 管线，
   沿用既有的 `eraDecay` 规则——**基础容量属于"能力上限"，按 `engine.ts:240` 的既有约定不退化为石器时代水准**。
3. E1 永远走"冻结档案"，**不读取任何新增字段**，保证 932s 基准与首屏逐字节一致。

## 九、实施顺序与验收

**实施顺序（低风险 → 高风险）**

| 批次 | 内容 | 风险 |
|---|---|---|
| **① 补 E2 断链** | 粮仓双效（+300 木 / +300 石）；不改任何现有数值 | 低（E2 无回归基准） |
| **② 抽档案** | 把 `getResourceStorage` 的 switch 抽成 `STORAGE_PROFILES`，E1/E2 逐位对齐 | 中（碰 E1 代码路径，须跑字节比对） |
| **③ 逐代落地** | E3 → E4 → E5 → E6 → E7，每代补存储建筑 + 基础容量阶梯 | 随各代配平定稿推进 |
| **④ 保真维度** | 接入损耗率（先做 E2 的食物腐败，与 `seasons-plan.md` §3.3 合并） | 中（影响配平，需重跑模拟） |
| **⑤ E8** | 待 E8 文档撰写后设计 | — |

**验收标准**

- [ ] **E1 beeline 门槛仍为 932s**；E1 首屏与中期存档渲染与基线**逐字节一致**
- [ ] 基础资源容量在 E1→E7 **严格单调递增**（可写一条断言在 `simulate.ts` 里跑）
- [ ] 每一代的**起始状态资源量 ≤ 该代基础容量**（即"装得下下一代的入场券"）
- [ ] 每个时代的建筑集里，**至少有一项标记为「存储」方向**（可用 grep 校验）
- [ ] 抽档案后，E1/E2 的 `getResourceStorage` 返回值与抽取前**逐位相等**

**明确不做的事（边界）**

- ❌ **不给 E1 增加存储建筑或科技**（保护冻结的回归基准；E1 的 500 木/石在其成本尺度下够用）
- ❌ **不给经验 / 知识 / 研究点设容量上限**（会瘫痪研究队列）
- ❌ **不做随机损耗**（存储失效必须是**可规划**的确定变量，与季节系统的铁律一致）
- ❌ **不改动 E2 已实现的粮仓 / 陶窑数值**（`800 / 0.15 / min 3`），只在其上**追加**基础容量效果
