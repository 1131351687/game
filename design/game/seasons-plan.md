# 季节系统 · 规划（待实现）

> **状态**：📋 **规划中 —— 本文件只描述设计意图，暂不实施**
> **决定时间**：2026-09-11
> **关联**：[`eras/E2-sedentary.md`](./eras/E2-sedentary.md) §1（季节循环）、[`01-core-loop.md`](./01-core-loop.md)（时代骨架）
> **一句话**：把季节从"E2 的一张农业倍率表"升格为**贯穿全时代的通用节律系统**——它同时作用于**生育**、**产量**，以及各时代专属的其他因素。当前只落了最基础的两条，其余全部暂缓。

## 一、当前实现基线（已存在，本规划不推翻）

E2「农业」科技点亮的只是季节系统的**最小切片**，共三条：

| 已实现项 | 数值 | 作用对象 | 代码位置 |
|---|---|---|---|
| 农业倍率 | 春 0.5 / 夏 1.0 / 秋 2.5 / 冬 0.05 | 农夫（谷物产出） | `demo/src/game/season.ts`、`engine.ts:calcJobOutput` |
| 生长因子（生育） | 春 1.0 / 夏 1.2 / 秋 1.1 / 冬 **−0.15** | 人口增长率 `r` 的乘数 | `engine.ts:getPopulationGrowth` |
| 伐木 / 打石倍率 | 四季 1.0，冬 **0.7** | 伐木者 / 打石者 | `engine.ts:calcJobOutput` |

**开关**：科技 `agriculture` 的 `enableSeasons` 效果位（`aggregateEffects().seasonsEnabled`）。
**未开启时**：`getSeasonGrowthFactor` 恒为 1.0，E1 不受任何影响——**这是 E1 配平基准（beeline 932s）逐字节不变的前提**。

**设计基石（来自 E2 文档 §1，不得违反）**：四季倍率的**年均值必须 ≈ ×1.0**
（春 0.5 + 夏 1.0 + 秋 2.5 + 冬 0.05 = 4.05，÷4 = ×1.0125）。
季节只改变产出的**时间分布**，不改变**年总产出**。任何新增的季节因子都必须满足这条。

## 二、同时记录一条既有规则：人口增长的双重约束（**已实现，勿动**）

> 2026-09-11 明确的设计规则：**人口增加必须同时受「人口上限 K」与「当前食物」约束。**

### 公式

```
增长率/秒 = 基础增长率(r) × 火源因子 × 季节因子 × P × (1 − P/K) × 食物因子
```

| 约束项 | 作用方式 | 说明 |
|---|---|---|
| **人口上限 K** | 逻辑斯蒂项 `(1 − P/K)` | P=K 时**增长恰好归零**，人口不可能越过 K；K 因建筑/田地变动而升降时，人口会被"挤"回来 |
| **当前食物** | 食物因子，**为负时直接走饥荒分支** `−STARVATION_DECAY` | 食物见底 → 人口按 0.5/秒 下降，不受 K 与季节影响 |

### 实测验证（2026-09-11 探针）

**E1 远古**（火源正常，一级住所 K=8）：

| 场景 | 食物因子 | 增长率 | 效果 |
|---|---|---|---|
| 食物 0，1 采集者（产 0.5 > 耗 0.4） | 0.8 | +0.0360/s | 27.8s 增 1 人 |
| 食物 0，0 采集者（产 0 < 耗） | −0.2 | **−0.5000/s** | 2.0s 减 1 人 |
| 食物 500，0 采集者（**存量足但断流**） | 0 | **0（冻结）** | 人口停住，不涨不掉 |
| 食物 500，P 顶到 K=8 | 0.8 | **0（冻结）** | **K 上限生效** |
| 食物 500，P=7（差 1 人到 K） | 1.0 | +0.0262/s | 38.1s 增 1 人 |

**E2 定居**（夏，seasonR=1.2，K=4+3×民居 4=16）：

| 场景 | 食物因子 | 增长率 | 效果 |
|---|---|---|---|
| 谷物 0（人均 0） | −0.5 | **−0.5000/s** | 2.0s 减 1 人 |
| 谷物 100（人均 10 < 12） | 0 | 0（冻结） | 人口停住 |
| 谷物 200（人均 20） | 0.4 | +0.0540/s | 18.5s 增 1 人 |
| 谷物 400（人均 40） | 0.8 | +0.1080/s | 9.3s 增 1 人 |
| 谷物 800（人均 80） | 1.0 | +0.1350/s | 7.4s 增 1 人 |
| 谷物 800，**冬**（seasonR=−0.15） | 1.0 | **−0.0169/s** | 59.3s 减 1 人 |
| 谷物 800，P 顶到 K=16 | 0.8 | **0（冻结）** | **K 上限生效** |
| 谷物 800，加盖 1 块田（K→28，P=16） | 0.8 | +0.1975/s | 扩 K 后立即恢复增长 |

**结论**：规则成立——**K 与食物缺一不可**，两者任一触底都会让增长归零或转负。

### ⚠️ 已知不一致点（列入待统一项）

两个时代判定食物因子的**方式不同**：

| 时代 | 判定方式 | 依据 |
|---|---|---|
| E1 | **流量型**：比较「当前产出 vs 当前消耗」，食物**存量**只作为饥荒开关 | `FOOD_FACTOR`（充裕 1.0 / 正常 0.8 / 紧张 0 / 饥荒 −0.2） |
| E2 | **存量型**：直接按「人均储粮」分档 | ≥60→1.0 / ≥32→0.8 / ≥12→0.4 / <12→0 / =0→−0.5 |

E2 的存量型更贴合"周期储备型"玩法（见 E2 文档 §1）；E1 的流量型则是"维持型"玩法的自然表达。
**是否统一由后续配平定稿决定**——统一会改变 E1 的 932s 基准，属于高影响改动，本次不动。

## 三、规划内容：季节应当影响什么（**未实施**）

E2 只让季节碰了"农业产出"和"人口增长"两件事。规划中的完整作用面如下。

### 3.1 生育（第一优先，本次规划的核心）

| 规划项 | 说明 | 状态 |
|---|---|---|
| 四季生育倍率分档 | 现在只有单一乘数（1.0/1.2/1.1/−0.15）；规划细化为**受孕季节 × 出生季节**两段 | ⬜ |
| 冬季"生育停滞"而非"人口回落" | 当前冬季 r 为负，人口会**自然减少**。规划讨论：是保留净减少，还是改为"增速归零 + 死亡率上升"两条独立曲线 | ⬜ |
| 生育受人均储粮阈值调制 | 生育倍率再乘一层"够不够吃"的档位（与第二条的食物因子联动，而非相乘两次） | ⬜ |
| 死亡率独立成线 | 现在没有死亡率概念，冬季减少全靠 r<0 硬表达；规划把"出生"与"死亡"拆开，便于后面加疫病/战争 | ⬜ |

**为什么指向"生育"**：史实上，前工业农业社会的出生率存在明显季节性（晚冬 / 早春为峰），与农忙—农闲节律、营养供给同步。把这条做进机制，E2 的"秋收—冬守—春生"才形成闭环，而不是只有"秋收"一件事。

### 3.2 产量（已有基线，待横向铺开）

| 规划项 | 说明 | 状态 |
|---|---|---|
| E2 农业 / 伐木 / 打石 | **已实现**（见第一节） | ✅ |
| 季节 × 岗位敏感度表 | 现在"是否受季节影响"是**硬编码在 `calcJobOutput` 的 if 分支**里；规划改为数据驱动：每个岗位在 `SeasonProfile` 里声明自己的四季倍率 | ⬜ |
| 后续时代的产出面 | 冶炼（E3）、工业（E6）、农业机械化（E6）、光伏（E7）各自的季节敏感度 | ⬜ |
| 渔猎 / 采集的季节性 | 采集者、猎人目前无季节波动；规划讨论是否给"春季采集加成 / 冬季狩猎加成" | ⬜ |

### 3.3 其他相关因素（全量清单，按时代）

| 因素 | 适用时代 | 说明 |
|---|---|---|
| 牲畜繁殖与冬季掉膘 | E2 | 现在牲畜只受"饥荒存活率"影响，与季节无关。规划：夏秋增重、冬季掉膘 |

| 施工进度 / 建筑效率 | E3+ | 冬季施工减半，把建材需求与季节绑定 |

## 四、数据结构草案（供未来实施参考，本文件不实现）

目标是把"季节影响什么"从 `calcJobOutput` 里的 if 分支，改为**按时代注册的数据表**：

```ts
/** 单季 × 单时代的完整倍率档案 */
export interface SeasonProfile {
  eraId: EraId;
  /** 农业类产出倍率（农夫、田地） */
  agriMul: number;
  /** 采集类产出倍率（伐木、打石，冬季 0.7） */
  loggingMul: number;
  /** 生育倍率 —— 作用于人口增长率 r */
  birthMul: number;
  /** 死亡率倍率（预留，当前无死亡率概念） */
  mortalityMul?: number;
  /** 施工速度倍率（预留） */
  buildSpeedMul?: number;
  /** 事件触发权重倍率（预留） */
  eventWeightMul?: number;
}

/** 按「时代 → 季节」索引；缺省一律取中性档案 */
export const SEASON_PROFILES: Record<EraId, Record<SeasonId, SeasonProfile>>;
```

**迁移原则**：

1. `getSeasonGrowthFactor(elapsed)` → `getSeasonProfile(era, elapsed).birthMul`，**E2 返回值必须逐位相等**（1.0 / 1.2 / 1.1 / −0.15）才允许合入
2. 未注册的时代自动回落到"全 1.0 中性档案"，保证 E3–E8 上线前不影响任何现有配平
3. E1 永远走中性档案（`seasonsEnabled === false`），932s 基准不受影响

## 五、暂缓理由（为什么现在不做）

1. **E2 的手感还没在浏览器里验证过**。目前只有 `simulate.ts` 的曲线，没有真实点击体验；在没验过的机制上再叠一层，风险不可控。
2. **跨时代季节表依赖各时代配平定稿**，而 E3–E8 目前只有设计文档（E8 尚未撰写），没有可填的数值。
3. **过早抽象会污染回归基准**。E1 的 beeline 932s 与"首屏逐字节不变"是当前唯一的质量护栏，任何改 `getSeasonGrowthFactor` 的改动都可能碰碎它。
4. **生育节律是全局量**。一旦跨时代生效，所有时代的通关时长都会变——这属于整体配平，不该在单代（E2）还没定稿时先做。

## 六、前置条件与验收

**开始实施的前置条件**

- [ ] E2 在浏览器内实机验证通过（季节条、越冬预报、谷仓溢出都有真实反馈）
- [ ] E2 跃迁条件定稿（含「完整度过 ≥8 个冬季」，目前未实现）
- [ ] E3–E7 配平表定稿
- [ ] E1 侧确认：`seasonsEnabled=false` 路径不读取任何 `SeasonProfile`

**验收标准**

- [ ] E1 beeline 门槛仍为 **932s**；E1 首屏与中期存档渲染与基线逐字节一致
- [ ] E2 四季 `birthMul` 与现值逐位相等（迁移不改行为）
- [ ] 每个新增倍率的**四季年均值落在 0.98–1.02**（守住"不改变年总量"铁律）
- [ ] 未定稿时代取中性档案，对现有通关时长零影响

**明确不做的事（边界）**

- ❌ 不做随机天气 / 抽卡式季节（E2 文档已明确否定："季节是必须被规划的确定变量，不是赌运气的随机数"）
- ❌ 不做半球 / 纬度差异（留给 P2 平行文明的起源选择）
- ❌ 不改动 E2 已实现的四项倍率数值（0.5 / 1.0 / 2.5 / 0.05 等）
